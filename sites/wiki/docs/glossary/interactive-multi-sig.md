# 交互式多签（Interactive Multi-Sig）

> **一句话定义：** 要求所有共签人在签名过程中实时协作、才能产出一笔有效多签交易的签名模型。

交互式多签是这样一类多签方案：共签人在签名时必须主动相互通信，而不是各自独立签名、再在链下把结果拼起来。

对比一下：

- **非交互式多签**（经典 `OP_CHECKMULTISIG`、P2SH、P2WSH）。每个共签人用自己的私钥独立给交易签名，脚本在链上把各个签名合并。除了传递部分签名交易（通常通过 PSBT）之外，签名者之间根本不需要交谈。
- **交互式多签**（MuSig2、FROST）。共签人参与一个多轮协议，每人贡献随机数和部分签名，必须以特定的密码学方式合并，才能产出一个有效的 Schnorr 签名。

为什么交互式有时值得付出复杂度：

- **链上只留聚合签名。** MuSig2 或 FROST 签名会话的产物是一个 64 字节的 Schnorr 签名，看起来和单签花费一模一样。相比链上出现 N 个签名的经典 N-of-M 多签，隐私和手续费都有显著节省。
- **门限更灵活。** FROST 支持 m-of-n 门限——任意 m 个签名者即可产出签名，不再死板地绑在 1-of-1 或 n-of-n 上。经典多签是刚性的；聚合门限在数学上更丰富。

交互式多签的代价：

- **协调开销。** 共签人需要同时在线（至少要在协同的通信轮次里出现）。对跨时区团队或人类签名者来说，这是实打实的运营摩擦。
- **状态管理。** 聚合签名协议是有状态的，签名者必须在各轮次之间小心跟踪随机数。状态丢失可能中断签名会话，最坏情况下会泄露私钥。
- **实现复杂度更高。** 经典多签成熟且久经考验；MuSig2 较新（BIP 327 于 2023 年标准化），实现层面更容易被 bug 咬到。

2026 年的生产现状：

- **闪电通道构造**越来越多地使用交互式多签（协作通道状态用 2-of-2 MuSig2，取代经典 2-of-2）。
- **联盟式设置**（Fedimint、Liquid 的 functionary）在试验 FROST。
- **主流个人多签**（Sparrow + 硬件钱包）出于运营原因仍用经典多签——非交互式签名更贴合人类的工作流程。

大方向是聚合式/交互式多签的采用会越来越多，但迁移是渐进的。两种形态会共存多年。
